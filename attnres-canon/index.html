NextTransformer · Arena v1

Opus 如何找到 AttnRes-Canon：一次架构探索的 Discovery Trace

葛羿2026 年 11 月约 10 分钟阅读

摘要

我们在 NextTransformer 的 Arena v1 上做了一次 auto research 尝试，让 Claude Opus 5.5 自己设计和筛选 Transformer 架构。整个过程分为前期探索、workflow 设计与三轮搜索，以及最终的完整训练。搜索阶段每个候选训练 2,000 步，约为完整训练步数的 4%，只看训练 loss 和 dev split 上的 BPB，探索与搜索合计的算力不超过总预算的三分之一；胜出者再按固定协议从头训练 49.152B token，训练 FLOPs 与参考成本相差不超过 1%，按 CORE-22 得分排名。全程由人审批计划和预算，候选的设计与去留都交给 agent。最终跑出来的 AttnRes-Canon 结合了 Full AttnRes 与四处 Canon 层：相比 Block AttnRes，它在搜索中的 dev BPB 低 0.0038；完整训练后 CORE 得分为 35.99，高出 2.0 分，验证 BPB 低 0.0024，两项在已发布结果里都排第一。

1. Agent 的前期探索

这次交给 Opus 的任务很直接：在 Arena v1 里，数据、训练步数和每步计算量都固定，只许改 Transformer 的模型结构，看看完整训练后能不能在 CORE-22 上超过已发布的方法。

难处在于完整训练一轮要上千 GPU 小时，搜索阶段根本没法把每个想法都跑到底。Opus 只能让每个候选先跑一小段短程训练，靠 dev split 上的 BPB（bits per byte，每字节的预测损失，越低越好）去估最终表现。要是这把尺子本身量不准，后面试再多改动也是碰运气。所以在动手改模型之前，它先花了约 150 GPU 小时做前期探索，确认两件事：研究环境里的训练和正式训练是不是一回事，训练截短以后排出来的名次还准不准。

研究训练器和正式训练器是一致的。同一个方法在两边各跑 512 步，第 1 步的 loss 完全相同，后面的细微差别只来自 GPU 运算的非确定性，平均不到 0.004。

真正棘手的是训练怎么截短。最自然的想法是把完整的学习率 schedule 压缩进 512 步（约占完整训练的 1%）：先拿 11 个已有完整成绩的方法各跑一遍，再和它们完整训练后的名次对比（图 1）。

压缩 schedule 排不准名次。两组排名的 Spearman 相关只有 0.40（1 表示名次完全一致），远低于事先定下的 0.85 门槛；在最终 BPB 相差超过 0.005 的 46 对方法里，短程训练只排对了 31 对。偏差还按结构家族一边倒：从短程到完整训练，四个 loop 类方法（同一组层重复执行）名次全部往下掉，四个 linear attention 方法全部往上走，DeepLoop 从第 3 掉到垫底，KDA 从第 8 升到第 2。提前到来的学习率衰减讨好了收敛快的 loop 结构，却让慢热的 linear attention 还没发力就收场了。

另一种做法干脆不压缩，直接截取正式 schedule 的前 N 步，下文称为前缀。用已发布的完整训练曲线回测同样 11 个方法，同样在 500 步左右，前缀的 Spearman 是 0.72，比压缩 schedule 的 0.40 高出一大截，可见是压缩本身帮了倒忙；取到前 2,000 步时，Spearman 达到 0.92，过了预设的门槛（图 2）。

尺子就此定下：不碰学习率 schedule，直接跑正式 schedule 的前缀，512 步只筛掉明显跑崩的候选，到 2,000 步再排座次、定胜负。

2. 搜索 Workflow 设计

尺子定准之后，Opus 把这几条结论整理成一套搜索规则（图 3、表 1），经操作者批准后锁死阈值：最多搜三轮，总算力不超过 600 GPU 小时。

落地执行时还有两项具体约定：

  • 以 Block AttnRes 为靶子划定胜出线：搜索先跑 Arena 的 dense baseline 和当时已发布的最强方法 Block AttnRes；再用同一 seed 重跑一次 dense baseline，测得 2,000 步的运行差异 δ 约为 0.0004，据此候选要比 Block AttnRes 低 0.001 以上才算过线。
  • 单点改动与逐轮叠加：每个候选相对父模型只改一处，写明可证伪的假设并把 FLOPs 控制在参考成本的 ±1% 内；下一轮可以拿上一轮的候选当父模型，从而把多个改动逐轮叠起来。

3. 三轮搜索与完整训练

3.1 搜索全局与演进路径

搜索以 Block AttnRes 为起点，三轮共训练 12 个候选，其中 4 个越过胜出线（图 4）。连同 baseline 和噪声测量共耗费约 550 GPU 小时，控制在 600 的上限内。512 步的粗筛没有砍掉任何候选，当时最差的一个也只比 dense baseline 差 0.010。

第一轮五个候选其实无一过线。图中的蓝线把当时最接近过线的两个温和改动（Full AttnRes 与 Canon-A/C）保留下来，经第二轮扩展和组合、第三轮合流，才一步步攒出了最终夺冠的 AttnRes-Canon。

3.2 第一轮：单点改动与早期假象

Block AttnRes 把 23 层分成 8 组做跨层残差检索。第一轮在它上面试了五个单点改动，前三个出自近期论文，后两个调整深宽比与参数分配（表 2）。

跑满 2,000 步时没有一个候选越过 −0.0010 的胜出线，Full AttnRes（−0.0008）和 Canon-A/C（−0.0006）离得最近。Gate 的早期大幅领先是个假象：它在 512 步低了 0.0027，领跑全场，但优势到 1,000 步左右便消磨殆尽，2,000 步反而倒输 0.0006（图 5）。

3.3 第二轮：组合验证与边际贡献

规则卡死了在 2,000 步判胜负，却没禁止提前排下一轮。第一轮刚出 512 步成绩，Opus 就按当时的名次挑定了第二轮的组合方向，并补入两个同计算量的 MoE 变体 [4]（表 3）。急着看早期信号选方向，直接让 Gate 分走了一半组合名额。

这一轮有三个候选过线，早期排名却翻得比第一轮更彻底：前四名在 512 步和 2,000 步的次序完全颠倒（图 6）。搅乱早期排名的还是 Gate：512 步时，凡是带 Gate 的模型都比对应的无 Gate 版本低 0.0014 到 0.0031；到 2,000 步，这点差值全部退回零附近。

提交前，Opus 给 Full + Canon-A/C 和 Gate + Canon-A/C 写的理由几乎一模一样：两处改动作用在不同部位，收益理应叠加。结果前者稳稳过线，后者原地踏步。把每个改动拆出来看它加在不同父模型上的边际变化（图 7、表 4），原因一目了然。

  • Full AttnRes 和 Canon 各自都有稳定收益：无论加在哪个已测父模型上，两者在 2,000 步都压低了 dev BPB。
  • Gate 本身没有净贡献：三组边际值有正有负，幅度与同 seed 重跑噪声相当；Full + Gate 能擦线过关，全靠 Full AttnRes 托底。

“作用部位不同就能叠加”只有在单件真有效时才成立，零加正数不会变成两份收益。这两组对照坐实了 Gate 没带来增量，第三轮就此将它剔除。

3.4 第三轮：共同父模型对照与最终组合

吃过早期信号的亏，Opus 在第三轮放慢节奏，等第二轮跑到中后段再做决定。此时站得住脚的只剩 Full AttnRes 和 Canon，而第二轮恰好有两个候选都在同一个父模型 Canon-A/C 上各走了一步：一个改成 Full AttnRes，另一个补齐 B/D 两处升为 Canon-A–D。放到共同父模型下同台比对，到 1,536 步两者都比 Canon-A/C 低约 0.002（图 8）。剩余预算只够再跑一个候选，Opus 没等 Canon-A–D 走完最后几百步，就拍板把两者合成为 AttnRes-Canon。

AttnRes-Canon 在 2,000 步拿到 0.7965，比 Block AttnRes 低 0.0038，夺得整场搜索头名（表 5）。它在 512 步还排在 Gate + Canon-A/C 后面屈居第二，768 步起便一路领跑。整套改动只比 Block AttnRes 多出约 127 万个参数，不到模型总量的 0.1%。

两个部件分工正交（图 9）。Block AttnRes 的子层只能读前面各组输出之和，好比只能翻每章摘要；Full AttnRes 拆开分组，让子层能逐层检索。Canon 层则是宽度为 4 的因果深度卷积，让当前 token 顺带融合前三个 token 的局部上下文；卷积权重初始化为零，训练起步时与不加 Canon 完全一致。一个打通深度，一个混合局部序列，Opus 据此猜想两者会互相借力，产生超出单件之和的收益。

表 5 的数字表面上顺着这个猜想走：从无 Canon 到 Canon-A/C 再到 Canon-A–D，把 Block 换成 Full 带来的额外降幅依次是 −0.0008、−0.0012 和 −0.0017。但相邻两档只差 0.0004 到 0.0005，与单次重跑的波动（约 0.0004）几乎同级，况且全是单 seed。现有数据与互补猜想相容，但还不足以坐实超加性效应。

3.5 完整训练结果

短程搜索停在恒定学习率阶段，完整训练要检验这份优势能不能扛过漫长的学习率衰减。我们将 AttnRes-Canon 移植为正式插件，逐项核对梯度一致后从头训练 49.152B token，耗时约 1,430 GPU 小时。评测看验证集 BPB 和 CORE-22（22 项任务扣除随机猜测水平后的归一化均分，下文乘以 100 展示，越高越好）。AttnRes-Canon 的 CORE 和验证 BPB 在 38 个已发布结果中双双排第一，紧随其后的都是搜索启动后才发布的跨层连接方法 mHC（表 6、图 10a）。

CORE 上 2.0 分的领先要打个折扣看。相对 Block AttnRes，22 项任务里 AttnRes-Canon 有 16 项更好、2 项持平、4 项更差；但高的 2.0 分里，BoolQ 一项是非判断题就占了 1.3 分（图 10b），剔除它之后领先缩小到 0.7 分。

验证 BPB 的领先贯穿全程，但进入衰减期后收窄了一半多。相对 Block AttnRes，它在 2,000 步低 0.0037，恒定学习率阶段拉开到近 0.006，进入线性衰减后被追回大半，终点定格在 −0.0024（图 11a、表 7）。

差距收窄主要是因为 Block AttnRes 自己在衰减期追得猛：同一时段 mHC 对 Block AttnRes 的优势也缩水大半，而 AttnRes-Canon 对 mHC 的领先从 −0.0015 到 −0.0011 几乎没松。表 7 最后一行是一个更极端的反例：另一位贡献者把第一轮那种 Gate 加在 dense baseline 上跑完正式训练，2,000 步时领先 0.0012（足以跨过本次搜索 0.001 的胜出线），衰减结束却倒输 0.0002。恒定学习率下攒出的优势能剩几成，只有跑完衰减才见分晓。

六次 CORE 评测取自同一轮训练的六个检查点（图 11b）。AttnRes-Canon 全程高于 Block AttnRes，但同 mHC 相比，前五次里有三次落后，直到最后一次才反超并领先 0.7 分。单次训练的检查点曲线还不足以说明换 seed 后名次是否稳固。

协议不卡的训练速度是另一笔代价。Arena 只约束每 token 的 FLOPs，不管实际耗时：在研究训练器里，AttnRes-Canon 的单步耗时是 Block AttnRes 的 1.66 倍（表 5），主要卡在四处 Canon 卷积缺少 fused kernel；这部分损耗能否靠定制算子追回，还有待实测。

4. 总结与展望

4.1 Arena v1 实验复盘

短程架构搜索成败的分水岭在于如何识别早期假象：训练前缀要长到足以筛掉昙花一现的领先，组合改动前还要在共同父模型上验明每个单件确实有效。

三阶段合计耗费 2,135 GPU 小时（表 8）：探索与搜索加起来约 700 GPU 小时，没有超过总算力的三分之一；移植阶段的梯度核对另用了约 50 GPU 小时，未计入下表。

Opus 做对的四件事：

  1. 先校准尺子再下场搜索：测出压缩 schedule 会系统性排错家族名次后，果断改用 2,000 步正式前缀。
  2. 守住单变量对照：每次相对父模型只改一处，并预先写下可被实验推翻的假设，使第二轮得以干净拆出边际贡献。
  3. 等长信号做组合决策：第三轮不再轻信 512 步名次，而是在共同父模型 Canon-A/C 上比对 1,536 步表现后再合流。
  4. 把外部文件当作持久记忆：四天里会话上下文被压缩了 7 次，每次都靠落盘的候选笔记和选择记录无缝续上。

暴露的四处短板：

  1. 计划与唤醒机制脱节：打算在 1,536 步拍板第三轮，却只在 512 步和 2,000 步挂了提醒，中间没人叫醒它，直到操作者催促才恢复推进。
  2. 先验未对齐当前协议：事先最看好的同计算量 MoE 连试两版，结果都排在末尾。
  3. 起初混淆了噪声口径：把同 seed 的 GPU 运行差异当成跨 seed 波动，虽然后来自己察觉并更正了文档，但始终没补跨 seed 复核。
  4. 选型只看损耗不看吞吐：筛选规则没有给单步耗时设上限，放过了明显变慢的卷积组合。

证据边界同样需要摆在明面上。全部结论建立在单 seed 之上，收益的稳定性与两部件是否真正互补，仍需多 seed 和完整规模消融来检验。搜索期间操作者只发过启动指令、几次进度询问和两次停摆后的继续提醒，没有挑过候选或给过方向暗示；候选筛选只用了 dev BPB，但当时尚无进程级隔离，Opus 事先读过仓库里已发布的完整训练记录。

4.2 Arena v2 预告

在 v1 里，阶段审批、预算看管、何时停手以及插件移植还得靠人兜底。Arena v2 打算通过四项升级把整套闭环彻底交给 agent 和 Gym：

  • 封闭容器隔离：研究全程在隔离容器内经由 Gym 接口执行，正式验证集与 CORE-22 对 agent 物理不可见。
  • 硬性 FLOPs 账本：每个会话固定分配 1.96×10²⁰ FLOPs（约合 v1 搜索里的 20 次 2,000 步 baseline 训练），训练、评估和失败重试一并扣减，同时记录模型调用的 token 与开销。
  • 自主实验设计：起点模型、对照组、候选数、训练步数与淘汰节奏全由模型自行裁量，不再预设固定步数或轮数。
  • 单文件直通评测：提交单一模型文件即由 Gym 自动拉起正式完整训练，省去逐阶段人工审批与手工移植。

按计划，Opus、GLM 和 DeepSeek 将在同等的 1.96×10²⁰ FLOPs 预算下各自独立跑完一轮研究，再用同一套完整训练协议对决各自找出的架构。针对本次暴露的短板，新版 workflow 草案还加入了最终候选的第二 seed 复核与步时上限。

这次实验跑通了单次会话内的架构探索闭环。下一步若要检验跨会话的自我改进（RSI），可以把自动决策触发、共同父模型边际核验等经验沉淀进下一代 workflow，在同等算力预算下与冻结的旧版 workflow 正面对照，看 agent 能否把踩过的坑真正变成更稳的搜索能力。
